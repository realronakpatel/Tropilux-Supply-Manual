01 · Start Here

Signing In & Navigation

Open the app in a browser, or install it: on an iPhone using Safari specifically (other iOS browsers can't install home-screen apps this way), a banner styled like a native install prompt — built into the app itself — offers to walk you through Share → Add to Home Screen. Dismiss it once and it won't ask again on that device. Sign in with your work email and password.

  1. Where you land on login depends on your role: Admin lands on the Dashboard; Office is routed straight into Item Requests instead; Warehouse, Staff, and Employee all land on the same page — Task Manager — since the Dashboard doesn't exist for them. (If you later click into a page your role can't open, you're bounced to that same fallback — except Office, which bounces to the Dashboard rather than back to Item Requests in that case.) A link inside a notification email can also drop you somewhere specific, like directly on the request or task it's about.
  2. The sidebar on the left is your map of the system, in this order: Dashboard, Task Manager, Timesheet, Item Requests, Misc Requests, Item Intake, Inventory, Used Inventory, Manual Entry, Orders, Shelves, Locations, Users, Reports & Notifications, Backups — this manual follows that same order. The sidebar only lists what your role can actually use; if a section here isn't in your sidebar, that's expected, not a bug.
  3. Your name, initials, and role sit at the bottom of the sidebar, next to the sign-out button. On a phone or narrow screen, the sidebar tucks behind a hamburger menu.
Live updates — the app keeps an open connection to the server. When a coworker approves a request, receives a shipment, or dispenses stock, your screen updates itself in the background — no refresh button to hunt for, on almost every list screen in the app. It's resilient, too: if your connection briefly drops (laptop sleep, a flaky network), it automatically reconnects and refreshes itself rather than quietly going stale. Two screens are the exception and don't update live: the Users directory only pushes changes to Admin (Office has to refresh to see a newly-added user), and Backups' daily-runs grid never live-updates at all.
Date filters, everywhere — most list screens (Item Requests, Misc Requests, Orders, Task Manager, Used Inventory, Manual Entry, Item Intake, Timesheet Reports) share the same date-range control: quick presets like Today, Yesterday, Past 7/30 Days, This/Last Week/Month/Year, plus a custom range — so you rarely need to type a date by hand.
Scoped access — your account can be restricted to specific properties and inventory categories by an Admin. If a screen looks lighter than a coworker's — fewer properties in a dropdown, fewer items in the catalog — that's your account's scope working as intended. One sharp edge: a non-admin account with no properties assigned sees an empty property dropdown everywhere, not "everything" — only an unscoped Admin sees all properties by default. Ask an Admin if something you need is missing.
Search is forgiving — item and property search ignores case, and treats curly quotes, straight quotes, and written-out measurements as the same thing — 72", 72-inch, and 72in all match each other.
Photos get resized — any photo you upload — on a request, a task, an intake — is automatically compressed and resized before it's saved, so it doesn't need to match your camera's original resolution. A replaced or orphaned photo isn't deleted outright, either — it's moved to an archive rather than erased, in case it's needed again.
Staying current — when a new version of the app ships, a "Reload / Later" prompt appears so you can pick up the update on your own schedule instead of being forced out of what you're doing.
Locked out? There's no self-service "forgot password" — if you can't sign in, ask an Admin to reset your password or check whether your account has been deactivated.

03 · Daily Operations

Task Manager

A board of six task types tied to the apartment lifecycle, each with its own color and icon: Maintenance, Move In, Move Out, Transfer, Billing, Admin. The page has two views: Task List (browse) and Assign Task (create).

BrowsingTask List

Type tabs across the top show live counts for each of the six task types. Within a type, scope tabs narrow the list to All, Assigned to Me, or Assigned by Me (Admin gets the full "All" view by default). Status pills filter by Pending, Awaiting Admin, or Completed. Further filters cover location, staff member, priority, whether it's recurring, free-text search, and a date range. Admin/Office can export the current filtered view to CSV.

CreatingAssign a Task

Pick the task type, assign one or more employees, set a deadline and a priority (Low or Urgent). Maintenance, Admin, and Billing tasks can all be made recurring — Daily, Weekly, Bi-Weekly, Monthly, Quarterly, Bi-Annually, or Annually — which automatically spawns the next occurrence as soon as one is completed.

Creating and reassigning a task isn't locked to Admin/Office the way approvals are — any signed-in role can technically do both. In practice it's Admin/Office who set up property-wide tasks, but don't be surprised if a coworker in another role can too.

Maintenance & AdminSimple Tasks

A free-text description with photo uploads. Every assignee marks their part done; for Maintenance, Admin/Office still gives a final close once everyone has confirmed. Admin-type tasks close automatically the moment all assignees confirm — no separate sign-off step.

Move In / Move Out / TransferChecklist Tasks

These three share a 7-point checklist, each item marked Yes/No with notes: Cleaning, Utilities, Appliances, Linens & Bathroom, Kitchenware, Inspection, Keys.

  • Move In — date, time, and deposit details, plus the checklist.
  • Move Out — the checklist, plus key return and a damage log: for each damaged or missing item, record the item (picked from the catalog), quantity, a damage type, a photo, and a description.
  • Transfer — runs the whole thing twice: once for the unit being left, once for the unit being moved into. These aren't independent — the Move-Out half has to be completed before the Move-In half can be started.

Move In and Move Out both lock down a few fields as required, not optional: an Actual Move-In/Move-Out Date, and a note on any checklist item marked "No." Move Out additionally requires electric and water meter readings before it can be completed. If "Keys returned" is marked No, the system automatically adds a damage-log entry for the missing key rather than making you log it by hand. All three checklist types finish the same way — a step literally labeled Verify Billing & Close Task, which asks Admin to confirm the charges set up when the task was created have actually been collected before it closes.

Automatic follow-through — logging damage on a Move Out or Transfer can automatically create a High-priority Item Request (to replace what's damaged) and an Urgent Maintenance task in the same step — notifying the right people without anyone having to remember to file a separate ticket. Any photo attached to a task uploads as soon as you pick it, and submission is blocked until every photo has finished (or been removed, if one failed).

BillingBilling Tasks

Each assigned person submits a note (readings, amounts, whatever the billing cycle needs). A progress chip shows how many of the assigned staff have submitted so far. Anyone except Office can mark a Billing task complete.

Assigned→ Pending (every assignee confirmed)→ Completed
Consensus model — a task only advances once every assigned employee has recorded their own completion. Admin alone can force-close a task outright, bypassing consensus; Admin or Office can confirm a single step on someone else's behalf if there's a holdup. Both kinds of override are logged, along with every ordinary status change and comment, in that task's activity log — and Admin/Office can also reopen or delete a task.

Edit or permanently delete an entry after submissionAdmin

05 · Daily Operations

Item Requests

The core daily loop: someone at a property needs something, the warehouse supplies it. (Shown in some places as Apartment Requests.)

Step 1New Request

Staff open a new request and work through: property → unit → rooms → items. A single request can cover multiple rooms, and each room can list multiple items.

  • Pick each item from the catalog (searchable, with a photo) — from either the new-stock catalog or the Used Pool directly — or type a description if it isn't a catalog item.
  • Set a quantity per item and an overall priority — Low, Medium, or High.
  • Give a reason per line — Damaged, Missing, Repair, New, or Other — plus a free-text note.
  • Attach a photo per item if it helps — a photo of the damage being replaced, for instance.

The system won't let you request more of an item than currently exists in stock — if you split one item across two lines (say, some damaged and some new), the check adds those lines together rather than checking each alone — and it warns you if the same item was recently dispensed to the same unit, to catch accidental duplicate requests.

The catalog picker doesn't show everyone the same detail: Admin and Warehouse see the real quantity on hand, while every other role — including Office — sees only an Available / Out of Stock badge rather than an exact count.

Step 2Review

WarehouseOfficeAdmincan act here
  • Approve All — clears every line as requested.
  • Partial Approve — adjust the approved quantity line by line; open to Warehouse as well as Admin/Office at this first-pass review stage.
  • Reject — declines the request outright.

If any line is flagged Requires Admin Approval — either because the item itself is flagged, or because the requested quantity crosses that item's approval threshold — a Warehouse approval doesn't finalize it. It routes instead to Pending Admin Approval, a second queue only Admin/Office can clear. Swapping in a substitute item at dispense time doesn't get around this: if the substitute is also flagged, the request bounces back to Pending rather than skipping the check. The Pending tab has its own toggle filter for "Requires Admin Approval" requests, plus filter chips by reason (Damaged/Missing/Repair/New/Other) with live counts.

Step 3Dispense

WarehouseAdmin
  • Disburse All — hands out every approved line in full.
  • Partially Disburse — hands out only some of the approved quantity. The request moves to Partial Dispensed, and a separate Disburse More Items button appears so the remaining approved quantity can be handed out later, in one or more further installments.
  • Substitute & Disburse — swap in a different catalog item (or a different pool — new vs. used) at the moment of hand-out, capturing that substitute's real price and stock impact.

Stock is deducted from whichever pool the item came from — for the new-stock pool, the oldest purchased batch is used first, so what the request "cost" stays accurate even as supplier prices move.

Step 4Return (when it applies)

Some catalog items — typically tools and equipment — are flagged Requires Return of Used Item. For those, the loop doesn't end at dispense:

  1. The requester (or anyone) marks the unused quantity as Return Unused Item.
  2. Warehouse then physically checks it back in with Accept Unused Item — this is the only moment stock is actually credited back. A flagged return never inflates the count just because someone said it was coming back.
This return step is skipped even on a flagged item if the line's reason was New or Missing — there's no used unit to send back in those cases, so no Pending Return record is created for that line.
Pending→ Pending Admin Approval→ Approved→ Dispensed→ Pending Returned→ Returned
Can end or split early Rejected· Partial Approved· Partial Dispensed
Finding things — the request list can be searched by property, unit, requester, item name, SKU, shelf, notes, or a substituted item's name. Roles with financial access see a running dollar total of what's been requested versus what's actually been handed out.
Exporting — a single request's PDF shows both the item's catalog photo and, separately, the photo you attached with your reason — a filtered-list PDF instead uses smaller thumbnails to keep it manageable. Either way, prices are automatically left off for roles without financial access; CSV export is also available. Reports & Notifications' Daily Usage Report can roll this activity up over a custom window of up to 31 days (7 by default), and each request's number (e.g. REQ-2026-168) starts counting at 101 each year, not 001.
Deleting — a request can be permanently deleted, not just rejected or archived — this is Admin-only and irreversible.

07 · Inventory & Stock

Item Intake

For things that show up without a purchase order — found items, donations, whatever gets pulled off a job site.

Step 1Submit Intake

AdminOfficeWarehouse

Pick an existing catalog item or type a new one, choose the destination pool (New or Used), a condition (Used–Good, Used–Fair, For Parts, or Damaged), a quantity, a shelf, and notes. A photo is required — the form won't submit without one.

Step 2Admin Review — this is where stock actually changes

Admin

Approve with one of: Add to New Inventory, Merge into Existing Inventory, Add to Used Inventory, Merge into Existing Used Inventory (a searchable picker lets you merge into a specific variant), Send for Repair, Discard / Trash, or Give Away. For the four add/merge decisions, the Inventory or Used Inventory record updates immediately — the count is live in the catalog the moment Admin approves, before Warehouse does anything further. "Add to New/Used Inventory" isn't a one-click choice — it opens the full item form right there, so category, min stock, unit cost, approval settings, and (if applicable) variant details all get filled in as part of approving. Or mark it Needs Info, which sends a message back to whoever submitted it (they can attach a new photo when they respond); it comes back for another look. It can also be marked Unresolved or rejected outright.

Merging can convert a simple item into a variant item — if you merge an intake in as a new variant of an item that's currently simple (one quantity, no variants) and already has stock, the system automatically converts that item to carry variants, folding its existing stock into a first variant. You'll be asked to type a name for that existing stock (up to 60 characters) so it has a label going forward — after this, the item behaves like any other variant item, including in Inventory and Item Requests.
Merging into the New Inventory pool can quietly tighten that item's rules: if either side required Admin approval, the merged item keeps that requirement (it's never loosened), and if both sides had a quantity threshold, the merged item keeps the stricter (lower) one. Merging into the Used pool only carries the approval-required flag over the same way — the existing item's quantity threshold is left as-is either way.

Step 3Warehouse Confirm

Warehouse

For decisions that need physical follow-through — sending something out for repair, discarding it, giving it away — the assigned person confirms it actually happened: Confirmed, Denied, or Unresolved, with notes. Admin/Office can also step in to deny or unresolve. For an add/merge decision, there's nothing left for this step to change in the catalog — it's a paper-trail confirmation, since the count already moved back at Review.

09 · Inventory & Stock

Used Inventory & Returns

What happens to items that come back.

Pending ReturnsUsed Pool

Pending ReturnsThe Disposition Workflow

When a returnable or used-pool item comes back from a property, it lands here as a pending return, tied to the request it came from. The list can be narrowed by a property dropdown, and exported to CSV.

  1. Received — Warehouse stamps it once it's physically back on-site.
  2. Split (optional) — a multi-quantity return can be split into two records with different quantities, so part of a batch can take one outcome and the rest another (e.g. half restocked, half discarded).
  3. Suggest Disposition — Warehouse or Admin proposes what should happen, with condition, notes, and an optional photo: Restock, Discard at Property, Discard at Warehouse, Give to Staff, Send for Repair, Keep for Parts, Lost/Stolen, or Different Item (Logged via Intake) — used when what physically came back isn't a match for what was dispensed, and has already been logged separately through Item Intake instead.
  4. Approve — Admin approves, rejects, or overrides the suggestion; Office can view but not act on it here.
  5. Execute — Warehouse or Admin carries it out. A Restock outcome requires confirming a condition and shelf location, and creates or updates the matching Used Pool record.

Anything sitting in the queue too long is flagged with an aging badge so it doesn't get forgotten.

A faster path also exists — Warehouse or Admin can skip the queue above entirely and hit Resolve, closing a return out in one step with any final outcome — Restock, Discard, Give to Staff, Send for Repair, Keep for Parts, or even Lost/Stolen — without a separate Admin approval, and even before the item has been marked Received. It runs in parallel to the Suggest → Approve → Execute flow, for when someone just needs to close something out on the spot. Items sent for repair come back through this same Resolve action once the repair's done — restocked (with condition/shelf) or any other final outcome.

11 · Inventory & Stock

Orders

Purchasing from suppliers.

AllPendingOrdered

All shows every order as a card. Pending narrows to drafts not yet sent. Ordered is a flat, searchable list of every still-outstanding line across every placed order — useful because a shipment arrives mixed and doesn't respect purchase-order boundaries. It has its own sub-filters, each with a live count: All, Outstanding, Nothing yet, Partly in, Received, and Closed.

Step 1Draft & Place

AdminWarehousedraft

Pick a supplier and add line items to a draft. The Review & Order step (Admin) locks in the actual quantity and unit cost per line, with optional notes per line, then submits it to the vendor.

The moment an order is submitted to the vendor, the catalog's listed unit cost for each ordered item updates to match — before anything has actually arrived. This is separate from the FIFO cost layers used to price a dispense, which only get created once a line is actually received; it just means the price shown on the Inventory page can shift as soon as an order goes out, not only once it's in.

Step 2Receive

WarehouseAdmin
  • Receive All — a one-click close for a fully-arrived order.
  • Partial — a shipment modal with a per-line quantity-received stepper and progress bars, distinguishing what's "arriving now" from the running "total received."
  • Per-line controls — Receive, Correct, Mark Not Received, or Reopen a single line from the flat Ordered list, without touching the rest of that order. Two people can receive different lines of the same order at the same time without conflicting.

Receiving more than was ordered, walking back a quantity already marked received, and marking a line Not Received are all Admin-only — Warehouse's per-line controls are otherwise Receive, Correct, and Reopen.

Good to know — every receipt is recorded at its actual cost, and when items are later dispensed from Item Requests, the oldest-purchased batch is used first — so reported costs stay accurate even as supplier prices change over time. Order and per-line history is viewable by Admin/Warehouse — opening history on a single line shows both that line's own events (received, corrected, closed, reopened) and a second section for how that item has moved warehouse-wide, not just on this order.
Exporting — PDF export comes in a financial version (with prices, Admin/Office) and a warehouse-safe version (no prices, also open to Warehouse) — a single order's PDF shows each line's real catalog photo, while a filtered-list PDF uses smaller cached thumbnails to keep it manageable. 16 · Administration

Backups

Admin-only. A defined set of core collections — users, properties, shelf locations, inventory (new and used), stock lots, pending returns, orders, item requests, misc requests, manual entries, item intakes, tasks, and timesheets — is backed up automatically once a day, written to two independent places (Google Drive and cloud storage), so a failure in one doesn't take out both copies.

What's not included — the backup does not capture audit/history logs — the records behind the "History" views you'll see on Inventory, Orders, Used Inventory, and Pending Returns — or archived item photos. Day-to-day stock, requests, and orders are fully protected; the detailed "who changed what and when" trail is not. Keep that in mind before relying on a restore to reconstruct exactly what happened, not just where things ended up.

The main screen is a grid of daily runs: status (Completed / In Progress / Failed), size, and what triggered it. A Run backup now button starts one on demand — though the daily backup itself is actually triggered from outside the app, by a scheduled job that runs overnight (roughly 2–3am); a failed run is logged as Failed and doesn't hold up the next day's backup. Pre-restore safety snapshots are hidden from this grid by default — a "Show pre-restore snapshots" checkbox reveals them, and unlike a regular backup, a snapshot can only be restored as the whole database, not one collection at a time. Opening a backup shows a per-collection breakdown with links to the stored files.

Restoring is deliberate — whether you restore the whole database or a single collection, the system automatically takes a safety snapshot first, and requires typing RESTORE to confirm. It can't be undone lightly, on purpose.
A backup run can also be permanently deleted — except a pre-restore safety snapshot, which is protected from deletion for 7 days after it's taken.

Roles at a Glance

One shared rulebook governs every screen in the app — roughly 140 individual permission switches, but they break down into a consistent shape per role:

RoleWhat they're for
AdminFull control of everything — financials, final approvals, edits and deletes, user management, permissions, backups and restore. The only role that can override a receiving quantity, edit a placed order, or force-close a task outright.
OfficeApprovals, reporting, and financial visibility from a desk — reviews and signs off on requests, sees cost figures, exports reports. Cannot dispense stock, receive shipments, or execute dispositions, and cannot mark a Billing task complete.
WarehouseThe physical operator — receives shipments, dispenses items and accepts returns, executes used-item dispositions, keeps shelves and photos current. Final approval sign-off still routes to Admin/Office.
Staff / EmployeeFront-line property staff — submit item and misc requests, work their assigned Task Manager checklists, log their own timesheets. Generally see only their own requests, tasks, and entries.
A handful of actions are more open than their module's overall theme suggests — for instance, creating and reassigning a Task Manager task is available to every role, not just Admin/Office. Where that's the case, it's called out in that module's own section above rather than in this summary table.
Within a role, an account can also be scoped to specific properties and inventory categories — so two people with the same role badge may not see exactly the same data.

Status Glossary

The same handful of status words recur across modules. Here's what each one means when you see it.

PendingSubmitted and waiting on someone's review — the default starting state almost everywhere.
Pending Admin ApprovalA first approval happened, but at least one line needs Admin/Office sign-off before it can move further (Item Requests).
Approved / Partial ApprovedCleared to fulfill — in full, or for only some of the requested lines.
Rejected / DeniedDeclined. Stops here; nothing is deducted from or added to stock.
Dispensed / Partial DispensedStock has physically left the warehouse for this request, in full or in part. A Partial Dispensed request can still be topped up via "Disburse More Items."
Returned / Pending ReturnedThe requester says an item is coming back — it isn't credited to stock until Warehouse also marks it Received.
DraftA purchase order being put together — not yet sent to the supplier.
OrderedSent to the supplier and awaiting delivery. The catalog's listed cost updates at this point too, ahead of anything arriving.
Received / Partly In / ClosedHow much of an order's line items have actually arrived; "Closed" is the current label for a line marked not received.
AssignedA task has been created and handed to one or more staff.
Awaiting AdminA Task Manager status filter for tasks where every assignee has confirmed but final sign-off is still outstanding.
CompletedEvery assignee has confirmed, and (where required) Admin/Office has given final sign-off.
Needs InfoSent back to the submitter for more detail before review can continue (Item Intake).
Disposition SuggestedWarehouse or Admin has proposed what should happen to a returned item — restock, discard, repair, etc.
ExecutedAn approved disposition has actually been carried out — e.g. the item is now back on the shelf in the Used Pool.
Different Item (Logged via Intake)A Pending Return disposition meaning what physically came back wasn't a match for what was dispensed — it's handled separately as its own Item Intake instead of being restocked here.
UnresolvedNeither confirmed nor denied — left open for follow-up (Item Intake, Pending Returns).
AgingA visual flag on anything that's sat in a queue — usually Pending Returns — longer than expected.
